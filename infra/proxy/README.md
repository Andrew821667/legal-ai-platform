# Прокси-канал до Telegram (Mac mini)

Telegram напрямую с боевого хоста недоступен, поэтому все боты и публикация
постов ходят через локальный xray-балансировщик на `192.168.64.1:10811`
(`TELEGRAM_API_PROXY_URL` в `.env`). Адреса VPN-узлов провайдер ротирует
постоянно — из-за блокировок, — поэтому пул пересобирается автоматически.

Файлы здесь — **источник**; на хосте лежат копии:

| Файл в репозитории | Путь на Mac mini |
|---|---|
| `xray-balancer-sync.py` | `/usr/local/sbin/xray-balancer-sync.py` |
| `xray-proxy-watchdog.sh` | `/usr/local/sbin/xray-proxy-watchdog.sh` |
| `ru.legalai.xray-balancer-sync.plist` | `/Library/LaunchDaemons/` |
| `ru.legalai.xray-proxy-watchdog.plist` | `/Library/LaunchDaemons/` |

## Как это работает

**Синхронизация пула** (`xray-balancer-sync.py`, раз в 30 минут):
1. Читает подписку провайдера (User-Agent `v2rayNG/1.8.0` — на другие клиент
   получает HTML или 500).
2. Выбрасывает служебные заглушки: и по названию узла, и по нерезолвящемуся
   адресу (`app.deprecated` — сообщение провайдера, а не сервер).
3. **Проверяет каждый узел TCP-подключением** и отбрасывает недоступные.
   Заблокированный адрес перестаёт отвечать раньше, чем провайдер уберёт его
   из подписки; в конфиге такой узел хуже, чем его отсутствие — балансировщик
   тратит на него попытки и может залипнуть.
4. Ставит первыми узлы «белых списков» — они устойчивее к блокировкам.
5. Складывает пул в детерминированном порядке, поэтому перестановка узлов в
   выдаче подписки сама по себе больше не вызывает перезагрузку балансировщика
   (раньше он перезагружался в ~86% циклов, каждый раз обрывая ботам
   long-polling).
6. Перезагружает балансировщик, только если набор узлов реально изменился.

**Watchdog** (`xray-proxy-watchdog.sh`, раз в 2 минуты):
1. Проверяет канал: `curl -x http://192.168.64.1:10811 https://api.telegram.org`.
2. Одна неудача — ничего не делает (бывает разрыв на ровном месте).
3. Вторая подряд — пересобирает пул (мёртвые узлы отсеются) и перепроверяет.
4. Если не помогло 5 проверок подряд (~10 минут) — шлёт алерт администратору
   в Telegram, пробуя все доступные прокси-инстансы по очереди.

Логи: `~andrej/Library/Logs/xray-balancer-sync.log`,
`xray-balancer.out.log`, `xray-proxy-watchdog.log`.

## Диагностика за минуту

```bash
# жив ли канал: 302 — да, 000 — пул мёртв
curl -x http://192.168.64.1:10811 https://api.telegram.org

# что решил последний цикл синхронизации
tail -8 ~andrej/Library/Logs/xray-balancer-sync.log

# какие узлы балансировщик считает мёртвыми
grep observatory ~andrej/Library/Logs/xray-balancer.out.log | tail -5

# история самовосстановлений
tail -20 ~andrej/Library/Logs/xray-proxy-watchdog.log
```

Важно: обычный интернет хоста при этом работает (ya.ru, ping проходят) — сбой
виден только на прокси, не путать с «упала сеть».

## Настройки (launchd, `EnvironmentVariables`)

| Переменная | Значение | Смысл |
|---|---|---|
| `XRAY_BALANCER_MAX_POOL` | 8 | сколько узлов держать в пуле |
| `XRAY_BALANCER_PROBE_TIMEOUT` | 3 | таймаут TCP-проверки узла, сек |
| `XRAY_BALANCER_ALLOW_LTE` | — | `1` включает медленные LTE-узлы (аварийный резерв) |

После правки plist перезагружать джоб именно так — `kickstart` новые
переменные окружения не подхватит:

```bash
sudo launchctl bootout system/ru.legalai.xray-balancer-sync
sudo launchctl bootstrap system /Library/LaunchDaemons/ru.legalai.xray-balancer-sync.plist
```

## Чего здесь сознательно нет

Статического «резервного узла» (`~andrej/.xray-balancer-extra-nodes.json`).
Он ставился в пул первым и переживал обрезку, но устаревал при каждой ротации
адресов: 23.09 провайдер сменил ему IP (`178.248.232.142` → `178.248.236.77`),
узел умер, а балансировщик продолжал ходить через него. Теперь живой набор
целиком берётся из подписки и проверяется на доступность — статический резерв
не нужен и вреден. Файл отключён (`.disabled`), поддержка в скрипте осталась
на случай, если подписка совсем перестанет отдавать рабочие узлы.
