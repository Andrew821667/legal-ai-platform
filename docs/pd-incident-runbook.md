# Personal Data Incident Runbook

Обновлено: 2026-10-01

Цель:
- зафиксировать базовый порядок действий при инциденте, связанном с персональными данными;
- не держать response plan только в памяти владельца проекта.

## 1. Что считать инцидентом

Инцидентом считать как минимум:
- утечку `.env`, токенов, TOTP-secrets, session secrets;
- несанкционированный доступ к `Postgres`, `SQLite`, backup-файлам или docker volumes;
- ошибочную публикацию данных пользователя в логах, чатах, выгрузках или публичных URL;
- компрометацию Telegram-бота, admin-панели или внешнего почтового канала;
- подозрение на доступ третьих лиц к переписке/лидам.

## 2. Первый час

1. Зафиксировать время и краткое описание инцидента.
2. Сохранить evidence:
   - логи контейнеров;
   - `git`/Actions events, если релевантно;
   - alert message;
   - список затронутых сущностей и сервисов.
3. Остановить расширение инцидента:
   - отключить внешний доступ;
   - остановить нужные контейнеры;
   - отозвать проблемный токен/ключ;
   - завершить активные admin sessions при необходимости.
4. Не удалять evidence до фиксации базовой картины.

## 3. Технические действия

1. Ротировать затронутые секреты по:
   - [secret-rotation-checklist.md](/Users/andrew/Мои AI проекты/legal-ai-platform/docs/secret-rotation-checklist.md)
2. Проверить:
   - Telegram bot token;
   - API keys;
   - admin session secret;
   - SMTP credentials;
   - DB credentials;
   - внешние service tokens.
3. Проверить, какие данные могли быть затронуты:
   - лиды;
   - история диалогов;
   - экспорт данных;
   - файлы/backup paths.
4. Зафиксировать фактический scope: какие пользователи и какие типы данных затронуты.

## 4. Журнал инцидента

Для каждого инцидента сохранить:
- дата и время обнаружения;
- кто обнаружил;
- техническая причина;
- затронутые сервисы;
- затронутые категории данных;
- действия по локализации;
- действия по ротации;
- решение по уведомлениям;
- дата закрытия инцидента.

## 5. Обязательные уведомления — сроки по закону

Если утечка (неправомерная или случайная передача, предоставление, распространение,
доступ к персональным данным) повлекла или могла повлечь нарушение прав людей,
уведомлять Роскомнадзор — обязанность оператора, а не решение «по желанию»
(ч. 3.1 ст. 21 152-ФЗ; порядок и форма — приказ РКН от 14.11.2022 № 187).
Отсчёт — с момента, когда инцидент обнаружен.

1. **≤ 24 часа — первичное уведомление РКН** через портал pd.rkn.gov.ru
   (раздел об инцидентах; оператор — физическое лицо, Попов А. В., ИНН 683302758241):
   - что произошло и предполагаемые причины;
   - какой вред мог быть причинён людям (какие данные, сколько человек — оценка);
   - какие меры уже приняты (см. раздел 2–3);
   - контактное лицо для связи с РКН.
2. **≤ 72 часа — результаты внутреннего расследования** через тот же портал:
   - установленные причины;
   - лица, чьи действия к этому привели (если установлены);
   - итоговый объём затронутых данных.
3. **ГосСОПКА** — оператор обязан информировать о компьютерных инцидентах, повлёкших
   утечку (ч. 12 ст. 19 152-ФЗ, порядок ФСБ; реквизиты приказа сверить перед применением).
4. **Людей, чьи данные затронуты**, закон уведомлять напрямую не обязывает, но если есть риск
   для них (паспорт, переписка по делу) — сообщить им и подсказать, что делать.

Шаблон первичного уведомления (заполнить и перенести на портал):

```
Дата и время обнаружения: …
Что произошло: … (например, доступ третьего лица к резервной копии базы)
Предполагаемые причины: …
Затронутые данные: … (ФИО, контакты, описания обращений, паспортные данные — да/нет)
Число затронутых лиц (оценка): …
Возможный вред: …
Принятые меры: … (ключи отозваны, доступ закрыт, контейнеры остановлены)
Контактное лицо: Попов Андрей Викторович, тел. …, e-mail …
```

Если уведомление не требуется (данные не затронуты, доступа не было), записать в журнал
инцидента, почему решили так, и кто решил. Отдельно решить и записать: нужно ли уведомить
подрядчиков и партнёров.

## 6. После инцидента

1. Обновить секреты и runtime env.
2. Проверить, что старые токены/сессии действительно больше не работают.
3. Провести post-incident review:
   - root cause;
   - missed detection;
   - что добавить в защиту/мониторинг;
   - какие документы/checklists обновить.
4. Обновить:
   - [project-control-checklist.md](/Users/andrew/Мои AI проекты/legal-ai-platform/docs/project-control-checklist.md)
   - [secret-inventory.md](/Users/andrew/Мои AI проекты/legal-ai-platform/docs/secret-inventory.md)
   - [secret-rotation-checklist.md](/Users/andrew/Мои AI проекты/legal-ai-platform/docs/secret-rotation-checklist.md)

## 7. Минимум перед следующим запуском

Сервис можно снова запускать наружу только когда:
- утечка локализована;
- критичные секреты ротированы;
- контур доступа проверен;
- понятно, какие данные были затронуты;
- уведомления РКН отправлены в сроки (24 и 72 часа) или записано, почему не требуются.
