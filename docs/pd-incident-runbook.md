# Personal Data Incident Runbook

Обновлено: 2026-03-11

Цель:
- зафиксировать базовый порядок действий при инциденте, связанном с персональными данными;
- не держать response plan только в памяти владельца проекта.

## 1. Что считать инцидентом

Инцидентом считать как минимум:
- утечку `.env`, токенов, TOTP-secrets, session secrets;
- несанкционированный доступ к `Postgres`, `SQLite`, backup-файлам или docker volumes;
- ошибочную публикацию данных пользователя в логах, чатах, выгрузках или публичных URL;
- компрометацию Telegram-бота, admin-панели или внешнего почтового канала;
- подозрение на доступ третьих лиц к переписке/лидам.

## 2. Первый час

1. Зафиксировать время и краткое описание инцидента.
2. Сохранить evidence:
   - логи контейнеров;
   - `git`/Actions events, если релевантно;
   - alert message;
   - список затронутых сущностей и сервисов.
3. Остановить расширение инцидента:
   - отключить внешний доступ;
   - остановить нужные контейнеры;
   - отозвать проблемный токен/ключ;
   - завершить активные admin sessions при необходимости.
4. Не удалять evidence до фиксации базовой картины.

## 3. Технические действия

1. Ротировать затронутые секреты по:
   - [secret-rotation-checklist.md](/Users/andrew/Мои AI проекты/legal-ai-platform/docs/secret-rotation-checklist.md)
2. Проверить:
   - Telegram bot token;
   - API keys;
   - admin session secret;
   - SMTP credentials;
   - DB credentials;
   - внешние service tokens.
3. Проверить, какие данные могли быть затронуты:
   - лиды;
   - история диалогов;
   - экспорт данных;
   - файлы/backup paths.
4. Зафиксировать фактический scope: какие пользователи и какие типы данных затронуты.

## 4. Журнал инцидента

Для каждого инцидента сохранить:
- дата и время обнаружения;
- кто обнаружил;
- техническая причина;
- затронутые сервисы;
- затронутые категории данных;
- действия по локализации;
- действия по ротации;
- решение по уведомлениям;
- дата закрытия инцидента.

## 5. Regulatory / compliance decision

Этот репозиторий не может автоматически решить, требуется ли регуляторное уведомление.
Владелец проекта должен отдельно принять и зафиксировать решение:

1. Требуется ли уведомление Роскомнадзора.
2. Требуется ли уведомление затронутых пользователей.
3. Требуется ли уведомление подрядчиков/партнеров.

Решение должно быть зафиксировано в incident journal, даже если ответ: `нет, не требуется`.

## 6. После инцидента

1. Обновить секреты и runtime env.
2. Проверить, что старые токены/сессии действительно больше не работают.
3. Провести post-incident review:
   - root cause;
   - missed detection;
   - что добавить в защиту/мониторинг;
   - какие документы/checklists обновить.
4. Обновить:
   - [project-control-checklist.md](/Users/andrew/Мои AI проекты/legal-ai-platform/docs/project-control-checklist.md)
   - [secret-inventory.md](/Users/andrew/Мои AI проекты/legal-ai-platform/docs/secret-inventory.md)
   - [secret-rotation-checklist.md](/Users/andrew/Мои AI проекты/legal-ai-platform/docs/secret-rotation-checklist.md)

## 7. Минимум перед следующим запуском

Сервис можно снова запускать наружу только когда:
- утечка локализована;
- критичные секреты ротированы;
- контур доступа проверен;
- понятно, какие данные были затронуты;
- решение по уведомлениям принято и записано.
