# Secret Rotation Checklist

Обновлено: 2026-03-11

Этот документ не хранит значения секретов. Он фиксирует порядок ротации, чтобы не пропускать связанные контуры и не ломать проект частичной заменой ключей.

## Когда ротировать обязательно
- после любого подозрения на утечку репозитория, ноутбука, volume или backup;
- после доступа постороннего к локальной машине;
- после публикации логов/скриншотов, где мог оказаться секрет;
- после смены администратора/оператора;
- перед переносом проекта с локальной машины на сервер;
- планово, даже без инцидента.

## Рекомендуемая периодичность
- Telegram bot tokens: раз в 90-180 дней или после инцидента;
- Core API scoped keys: раз в 90 дней;
- Web admin secrets (`PASSWORD_HASH`, `TOTP`, `SESSION_SECRET`): раз в 90 дней;
- LLM/API provider keys: раз в 90-180 дней;
- Postgres password: перед любым внешним деплоем и после инцидента;
- SMTP / analytics / GitHub integration tokens: раз в 180 дней.

## Порядок ротации без пропусков

### 1. Подготовка
- `[ ]` Понять, какие секреты ротируются и какие сервисы они затрагивают.
- `[ ]` Свериться с [secret-inventory.md](/Users/andrew/Мои%20AI%20проекты/legal-ai-platform/docs/secret-inventory.md).
- `[ ]` Подготовить новые значения заранее.
- `[ ]` Убедиться, что есть окно на рестарт контейнеров и smoke после замены.

### 2. Замена секрета
- `[ ]` Обновить локальный `.env` или целевой secret store.
- `[ ]` Не менять `.env.example`, если изменилось только значение, а не состав переменных.
- `[ ]` Если меняется связка (`POSTGRES_PASSWORD` + `DATABASE_URL`), обновить оба конца.
- `[ ]` Если меняется session/admin secret, понимать, что активные сессии будут инвалидированы.

### 3. Перезапуск и smoke
- `[ ]` Пересобрать/перезапустить только затронутые контейнеры.
- `[ ]` Проверить `docker compose ... config`.
- `[ ]` Проверить `healthcheck`.
- `[ ]` Проверить живой сценарий конкретного сервиса:
  - `[ ]` `lead-bot`
  - `[ ]` `reader`
  - `[ ]` `news admin`
  - `[ ]` `web admin`
  - `[ ]` `core-api`

### 4. Пост-ротация
- `[ ]` Удалить старые временные записи/backup, если они создавались.
- `[ ]` Зафиксировать дату и объем ротации в таблице ниже.
- `[ ]` Если была утечка, считать старый секрет скомпрометированным и не возвращать его.

## Частные сценарии

### Telegram bot token
- `[ ]` Выпустить новый токен у `@BotFather`.
- `[ ]` Обновить токен в `.env`.
- `[ ]` Перезапустить нужный bot container.
- `[ ]` Проверить `/start`, callback, критичный user flow.

### Core API scoped key
- `[ ]` Выпустить новый scoped key в `core-api`.
- `[ ]` Обновить все потребители этого scope.
- `[ ]` Убедиться, что старый ключ больше не принимается.

### Web admin secrets
- `[ ]` Сгенерировать новый `ADMIN_PANEL_PASSWORD_HASH`.
- `[ ]` Сгенерировать новый `ADMIN_PANEL_TOTP_SECRET`.
- `[ ]` Сгенерировать новый `ADMIN_PANEL_SESSION_SECRET`.
- `[ ]` Перезапустить `web`.
- `[ ]` Проверить login -> session -> logout -> logout all.

### Postgres password
- `[ ]` Обновить `POSTGRES_PASSWORD`.
- `[ ]` Обновить все `DATABASE_URL`.
- `[ ]` Проверить, что backend-сервисы поднялись и проходят healthcheck.
